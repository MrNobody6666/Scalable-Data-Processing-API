# Scalable Data Processing API

An out-of-core data join pipeline wrapped in a non-blocking FastAPI backend.  
Two approaches for background task execution are implemented and compared.

---

## Project Structure

```
scalable-data-api/
├── generate_data.py          # Generates ~500 MB test CSVs
├── join_service.py           # DuckDB out-of-core join engine
├── api_background_tasks.py   # Approach 1: FastAPI BackgroundTasks
├── api_celery.py             # Approach 2: FastAPI + Celery
├── celery_worker.py          # Celery worker definition
├── requirements.txt
└── README.md                 ← you are here
```

---

## Quick Start

### 1. Install dependencies

```bash
pip install -r requirements.txt
```

### 2. Generate test data (~500 MB each)

```bash
python generate_data.py
```

This creates `users.csv` (~5 M rows) and `transactions.csv` (~8 M rows).

### 3. Run the join standalone (optional)

```bash
python join_service.py
```

Produces `result.csv` — the INNER JOIN of both files on `user_id`.

## Approach 1 — FastAPI BackgroundTasks

**Start the server:**

```bash
uvicorn api_background_tasks:app --host 0.0.0.0 --port 8000 --reload
```

**Trigger a join:**

```bash
curl -X POST http://localhost:8000/trigger-join
# → {"job_id": "abc-123-..."}
```

**Check status:**

```bash
curl http://localhost:8000/status/<job_id>
```

## Approach 2 — Celery + Redis

**Prerequisites:** Redis running on `localhost:6379`.

```bash
# Terminal 1 — Start Redis (if not already running)
redis-server

# Terminal 2 — Start the Celery worker
celery -A celery_worker worker --loglevel=info --pool=solo

# Terminal 3 — Start the API
uvicorn api_celery:app --host 0.0.0.0 --port 8001 --reload
```

**Trigger a join:**

```bash
curl -X POST http://localhost:8001/trigger-join
# → {"job_id": "abc-123-..."}
```

**Check status:**

```bash
curl http://localhost:8001/status/<job_id>
```

## Assignment 1 — Out-of-Core Join Strategy

### Why DuckDB?

| Requirement | How DuckDB Satisfies It |
|---|---|
| **256 MB RAM limit** | `SET memory_limit = '200MB'` — DuckDB enforces this internally and spills to disk when needed. |
| **No full-file load** | `read_csv_auto()` streams rows lazily from disk; neither CSV is ever fully materialised in memory. |
| **Single dependency** | DuckDB is an embedded, zero-config OLAP engine — no external database server required. |
| **Performance** | Vectorised execution engine with parallel I/O; significantly faster than row-by-row chunk processing in pandas. |

### Alternative Considered — Pandas Chunked Join

A chunked pandas approach (iterating over `transactions.csv` in small DataFrames and merging against a partitioned `users.csv`) is also viable, but:

- Requires careful manual chunk sizing and memory accounting.
- Much slower due to Python-level iteration and repeated I/O.
- DuckDB's C++ engine handles the same logic in a single SQL statement with automatic memory management.

## Assignment 2 — Background Task Comparison

| Criteria | BackgroundTasks | Celery + Redis |
|---|---|---|
| **Setup complexity** | ★☆☆ Trivial — zero extra infra | ★★★ Requires Redis + worker process |
| **Scalability** | Single-process only | Horizontally scalable (add workers) |
| **Fault tolerance** | Task lost if server crashes | Tasks persist in Redis; workers can restart |
| **Resource isolation** | Shares CPU/RAM with API server | Worker runs in a separate process/machine |
| **Monitoring** | Manual (in-memory dict) | Flower dashboard, Celery events, etc. |
| **Best for** | Prototyping, light workloads | Production, multi-user, heavy workloads |

### Recommendation

- **Development / single-user**: Approach 1 (BackgroundTasks) is perfectly adequate and keeps the stack simple.
- **Production / multi-user**: Approach 2 (Celery) is the clear winner — it isolates heavy processing, survives crashes, and scales horizontally.

## API Reference

Both servers expose identical endpoints:

| Method | Path | Description |
|---|---|---|
| `POST` | `/trigger-join` | Start a join job. Returns `{ "job_id": "..." }` with HTTP 202. |
| `GET` | `/status/{job_id}` | Query job status: `pending → running → completed / failed`. |
| `GET` | `/health` | Health-check. |
| `GET` | `/docs` | Interactive Swagger UI (auto-generated by FastAPI). |

## Memory Verification

To confirm the 256 MB constraint is respected, run the join under a memory profiler:

```bash
# Option A — resource module (Linux/macOS)
/usr/bin/time -v python join_service.py

# Option B — tracemalloc snapshot
python -c "
import tracemalloc, join_service
tracemalloc.start()
join_service.perform_join()
current, peak = tracemalloc.get_traced_memory()
print(f'Peak Python memory: {peak / 1024 / 1024:.1f} MB')
tracemalloc.stop()
"
```

> **Note:** DuckDB allocates memory outside Python's `tracemalloc` arena.
> Use OS-level tools (Task Manager, `htop`, `psutil`) for the true picture.
> DuckDB itself is hard-capped at 200 MB via the `SET memory_limit` pragma.
