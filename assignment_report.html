Assignment 1 — Out-of-Core Data Join

Problem Statement

Perform an INNER JOIN on users.csv (~500 MB, 5 M rows) and transactions.csv (~500 MB, 10 M rows) on the user_id column, producing result.csv. The entire operation must fit inside a 256 MB RAM budget — ruling out loading either file fully into memory with pandas.read_csv().

Algorithm — DuckDB Streaming Out-of-Core Join

The solution uses DuckDB, an embedded analytical database engine designed for fast SQL execution. DuckDB's CSV scanner reads data lazily in chunks, never materializing entire files in RAM at once.

  • Memory Limit: DuckDB is configured with `SET memory_limit = '200MB'` to strictly stay under the 256MB system constraint.
  • Streaming Execution: The `COPY (...) TO 'result.csv'` query executes the join and streams the results directly to disk.
  • Disk Spilling: A unique temporary directory is provided for each job, allowing DuckDB to safely spill intermediate hash tables to disk if memory pressure is too high, avoiding OOM errors.

Complete Source — join_service.py (Part 1)

import logging
import os
import shutil
import time
import uuid
import duckdb

logger = logging.getLogger(__name__)
logging.basicConfig(level=logging.INFO, format="%(asctime)s  %(levelname)-8s  %(message)s")

BASE_DIR = os.path.dirname(os.path.abspath(__file__))

def perform_join(users_path=os.path.join(BASE_DIR, "users.csv"),
                 transactions_path=os.path.join(BASE_DIR, "transactions.csv"),
                 output_path=os.path.join(BASE_DIR, "result.csv"),
                 memory_limit="200MB") -> dict:
    
    start = time.perf_counter()
    con = duckdb.connect(database=":memory:")
    temp_dir = os.path.join(BASE_DIR, f"duckdb_tmp_{uuid.uuid4().hex}")
    
    try:
        con.execute(f"SET memory_limit = '{memory_limit}'")
        con.execute(f"SET temp_directory = '{temp_dir.replace(os.sep, '/')}'")
        con.execute("SET preserve_insertion_order = false")
        con.execute("SET threads = 2")

        query = f"""
            COPY (
                SELECT
                    u.user_id, u.name, u.email, u.age, u.city,
                    t.transaction_id, t.amount, t.date, t.category
                FROM read_csv_auto('{users_path.replace(os.sep, "/")}')       AS u
                JOIN read_csv_auto('{transactions_path.replace(os.sep, "/")}') AS t
                  ON u.user_id = t.user_id
            ) TO '{output_path.replace(os.sep, "/")}' (HEADER, DELIMITER ',');
        """
        con.execute(query)

        row_count = con.execute(
            f"SELECT count(*) FROM read_csv_auto('{output_path.replace(os.sep, '/')}')"
        ).fetchone()[0]
    finally:
        con.close()
        if os.path.exists(temp_dir):
            shutil.rmtree(temp_dir, ignore_errors=True)

    duration = time.perf_counter() - start
    logger.info("Join complete in %.2fs -- %s rows written.", duration, f"{row_count:,}")
    return {"rows": row_count, "output_path": output_path, "duration_seconds": round(duration, 2)}

Assignment 2 — Non-Blocking FastAPI

The join operation takes ~7 seconds of CPU and I/O time. Running it synchronously inside an HTTP handler would block the event loop, causing timeouts and denying service to other users. The solution exposes a POST /trigger-join endpoint that immediately returns a job_id (HTTP 202 Accepted), while the join proceeds asynchronously. Clients poll GET /status/{job_id} for status updates.

API Contract

# Trigger a join job
POST /trigger-join
  -> 202 Accepted
  -> { "job_id": "<uuid>" }

# Poll for status
GET /status/{job_id}
  -> 200 OK
  -> { "job_id": "<uuid>",
       "status": "pending | running | completed | failed",
       "error": "<human-readable message if failed>",
       "result": { "rows": 8000000, "output_path": "...", "duration_seconds": 7.55 } }

Approach 1 — FastAPI BackgroundTasks

FastAPI’s built-in BackgroundTasks mechanism runs the join function in a regular OS thread after the HTTP response has been flushed to the client. No external services or extra processes are needed.

Pros

  • Zero extra dependencies beyond FastAPI and Uvicorn.
  • Very simple to read and reason about.
  • Adequate for low-to-medium concurrency loads.

Cons

  • Thread shares the same process as the web server — CPU-heavy work can degrade API responsiveness.
  • In-memory job store: server restart loses all job state.
  • Requires manual semaphore to prevent 1000 requests from spawning 1000 joins and bypassing the 256MB limit.

import logging, os, threading, uuid
from datetime import datetime, timezone
from fastapi import BackgroundTasks, FastAPI, HTTPException
import join_service

app = FastAPI(title="Data Join API -- BackgroundTasks Approach")
jobs: dict[str, dict] = {}
MAX_CONCURRENT_JOINS = 1
_join_semaphore = threading.Semaphore(MAX_CONCURRENT_JOINS)

def _run_join(job_id: str) -> None:
    acquired = _join_semaphore.acquire(timeout=0)
    if not acquired:
        jobs[job_id]["status"] = "failed"
        jobs[job_id]["error"] = "Another join is already running. Try again later."
        return

    jobs[job_id]["status"] = "running"
    try:
        output_file = os.path.join(join_service.BASE_DIR, f"result_{job_id}.csv")
        result = join_service.perform_join(output_path=output_file)
        jobs[job_id]["status"] = "completed"
        jobs[job_id]["result"] = result
    except Exception as exc:
        jobs[job_id]["status"] = "failed"
        jobs[job_id]["error"] = str(exc)
    finally:
        _join_semaphore.release()

@app.post("/trigger-join", status_code=202)
async def trigger_join(background_tasks: BackgroundTasks):
    job_id = str(uuid.uuid4())
    jobs[job_id] = { "status": "pending", "result": None, "error": None }
    background_tasks.add_task(_run_join, job_id)
    return {"job_id": job_id}

@app.get("/status/{job_id}")
async def get_status(job_id: str):
    if job_id not in jobs:
        raise HTTPException(status_code=404, detail="Job not found")
    return {"job_id": job_id, **jobs[job_id]}

Approach 2 — Celery with Redis Broker

The join is submitted to a Celery worker backed by a Redis message queue. The API server only handles HTTP requests and enqueues tasks, completely isolated from the heavy data processing.

Pros

  • True isolation — the join never competes with the FastAPI event loop for the GIL.
  • Built-in concurrency controls (e.g., Celery worker concurrency limits) prevent unbounded resource consumption natively.
  • A crashing worker cannot bring down the web server process.
  • Persistent job state tracking via Redis backend.

Cons

  • Requires deploying and maintaining an external message broker (Redis).
  • More complex deployment architecture (requires starting a separate Celery worker process).

from celery.result import AsyncResult
from fastapi import FastAPI
from celery_worker import celery_app, run_join_task

app = FastAPI(title="Data Join API -- Celery Approach")

@app.post("/trigger-join", status_code=202)
async def trigger_join():
    task = run_join_task.delay()
    return {"job_id": task.id}

@app.get("/status/{job_id}")
async def get_status(job_id: str):
    result = AsyncResult(job_id, app=celery_app)
    response = { "job_id": job_id, "status": result.state.lower() }
    
    if result.state == "SUCCESS":
        response["result"] = result.result
    elif result.state == "FAILURE":
        response["error"] = str(result.result)
        
    return response
